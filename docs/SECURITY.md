# Security baseline

This is an implementation baseline, not a production certification.

## Implemented controls

- Private page loaders/actions resolve identity and event membership server-side. Production uses Better Auth; demo identities exist only in an explicitly validated non-production runtime mode. The Worker rejects missing, misspelled or contradictory `APP_ENV`/`DEMO_MODE` combinations before routing or consuming Queue work.
- Better Auth stores users, sessions, accounts and verification records in D1. Magic links are hashed, expire after five minutes and cannot create an uninvited account. New administrator/evaluator invitations carry an expiry, require an explicit same-origin event-selector confirmation before they grant access, and are then audited. Pending invitations with a missing/elapsed expiry and revoked memberships fail closed. Missing auth secrets or selected email-provider configuration fails explicitly; production accepts only Resend, while the local demo/development profiles select Mailpit without fallback.
- Public application sessions use an HttpOnly, SameSite cookie backed by a hashed D1 token. Verification codes expire after ten minutes, allow at most five failed attempts and are atomically consumed once. Demo mode never claims a code was emailed. Public form views omit password verifiers, private routing and raw persistence aliases.
- Production sign-in and public-application actions use D1-backed IP policies and, where an email identity is known, email/IP-email policies, plus server-verified Turnstile tokens. Missing production keys, connecting-IP identity, an unavailable verification service and rejected tokens fail explicitly. Demo/test mode omits the external widget without claiming production protection.
- Event API keys are high-entropy bearer credentials stored only as SHA-256 digests. They are event/organisation scoped, constrained to the declared scope vocabulary, optionally expiring, revealed once and revocable; use is timestamped. Mutation routes reject unsupported methods, and atomic idempotency records return only the exact saved result for a matching actor/command/request hash.
- Every private production query and mutation includes organisation and event scope. An authorised HttpOnly current-event cookie is explicit and audited; ambiguous, invalid or revoked context never falls back to `DEFAULT_EVENT_ID`. A table-driven route matrix covers owner, organisation/event administrator, committee chair, evaluator, submitter, speaker, pending/revoked/expired and cross-organisation access. Decision release is service-authorised: owners and administrators may release, while a committee chair also requires an explicit active-plan grant.
- Public programme UI, JSON and iCalendar resources read only the latest published schedule version. Event slugs are globally unique, and canonical programme/calendar-session URLs carry the selected event slug. Private API CORS allows only configured origins; published resources use public CORS.
- The Worker applies content-type, referrer, permissions, opener and content-security headers, plus HSTS in production. Embed `frame-ancestors` must be explicitly configured in every runtime mode.
- HTTP, Queue, scheduled and backup-Workflow entry points require a validated `SOURCE_REVISION`; production accepts only a 7–64 character hexadecimal Git revision, and readiness exposes that non-secret identifier. Request, Queue, scheduler, backup and communication-dispatch failure logs use bounded correlation/event/operation identifiers, provider labels and error classes without logging request bodies, URL paths, provider payloads, prompts, secrets, personal data or raw exception messages. Operator-facing detail remains in scoped durable operation records where recovery requires it.
- File bytes are stored in private R2 under opaque event/target/asset/version keys and downloaded only through authenticated, audience-scoped routes. Every event has a required strict file policy bounded by canonical maxima. Uppy multipart initiation, resume/ListParts, completion and final metadata commit reauthorise the target and revalidate current policy, reported R2 parts, assembled metadata and file signature. A browser resume hint never grants authority. Uploaded versions stay quarantined until an authenticated scanner callback records a clean verdict; missing signing/scanner configuration fails closed before claiming completion.
- Published form settings, resource/template identity and schedule session/content/notes belong to immutable versions. Draft changes cannot alter a live form, published resource/audience/attachment, automatic communication category or published programme/calendar payload before a claimed publication succeeds. Resource acknowledgements identify the exact published version.
- Schedule publication recomputes authoritative conflicts using event-timezone, room, speaker, capacity, track and required-resource rules even if the UI showed an older result. Event/version revision claims prevent concurrent setup or schedule changes from committing after stale validation.
- Communication and calendar flows persist intent, delivery/attempt rows and audit evidence before Queue/provider work. Provider execution uses renewable, random-token D1 leases that expire after 60 seconds. Expired `running` operations can be reclaimed after a crashed consumer; delivery under an active lease is delayed for 60 seconds; and completion/failure writes require the current token. Provider idempotency keys and uniqueness constraints protect retryable sends, while cancellation competes with the send claim instead of silently resurrecting cancelled work.
- Decision and submission notification consumers keep communication, delivery, operation-item and audit materialisation conditional on the operation remaining eligible. A stale duplicate that resumes after another consumer reaches a terminal state cannot recreate or send that work.
- Optional email contains an HMAC-signed, expiring unsubscribe link. Viewing the destination is read-only and an explicit POST confirms the category opt-out; optional-recipient selection and the final pre-provider claim both enforce active category preferences. Transactional email ignores those optional-message preferences, while provider complaint/suppression exclusions apply to every email kind.
- Resend delivery webhooks require a valid signed raw body, bounded replay timestamp and provider event ID. Duplicate receipts reconcile idempotently, and persisted receipts are reduced by precedence so a delayed success cannot reverse a bounce, suppression or failure. Complaint and provider-suppression events create an event-wide exclusion for future email to that address.
- Calendar lifecycle work binds each invitation to one current attempt and sequence. Rapid republication supersedes stale attempts, and a stale provider completion cannot overwrite the newer invitation state.
- Google/Microsoft calendar connection setup uses an authorised OAuth start/callback with signed short-lived state, encrypted refresh tokens and compare-and-set token refresh. Sender/domain and calendar administration remain server-authorised; missing provider applications and verification failures do not create connected records.
- Airtable and Accelevents credentials are encrypted at rest and event scoped. Airtable repository authority is explicit: managed-schema validation, durable commands and projection recovery fail closed, and D1 domain data is never substituted after an Airtable failure. Accelevents dry runs never write; terminal reconciliation CSVs are built from tenant-scoped immutable run snapshots and neutralise spreadsheet formulas.
- The event assistant reads only evidence permitted to the current server principal. Advisory contexts receive no mutation tools. Consequential tools create exact durable proposals requiring explicit approval; renewable execution leases, idempotent domain commands and audit records recover crashes without double execution. Organisation provider settings use owner-only compare-and-set/audit, and the selected Workers AI/OpenAI/Anthropic credential fails without fallback. OpenAI requests disable provider storage and use a pseudonymous safety identifier rather than raw participant identity.
- Queue configuration has bounded retries and a dead-letter queue. An active claim is retried after its 60-second lease window rather than being treated as a failure; unsupported operation messages are marked failed and audited instead of being reported as successful.
- Cookie-authenticated React Router mutations require an exact same-origin `Origin` header at the Worker boundary. Versioned APIs, provider webhooks and Better Auth routes retain their API-key, signature or Better Auth protections.
- The owner-only participant-retention workflow enforces the configured event boundary and legal hold, requires file-provider erasure first, uses bounded typed-confirmation batches, pseudonymises event participant links, revokes exclusive credentials and redacts embedded participant/provider identifiers. Completion creates an event tombstone and immutable evidence; D1 ingress guards prevent participant PII from being recreated while preserving audit/recovery bookkeeping.
- Audit records are append-only at the database layer. Implemented consequential flows—including event/form/resource changes, decisions, schedule publication, tasks, files, communications, calendars, integrations, assistant proposals/executions, API lifecycle and retention—append audit evidence.

## Outstanding production acceptance

- Provision and exercise Turnstile, private R2 signing credentials/CORS, the malware scanner and provider-side erasure. Unit/Worker boundaries do not prove the live widget, bucket or scanner.
- The current content security policy permits inline scripts and styles for the application build. A nonce/hash-based production policy and third-party provider allow-list are not complete.
- Exercise real Resend sender/domain/webhook delivery, Google/Microsoft OAuth, Airtable, Accelevents and external AI-provider paths with production-scoped credentials. No live-provider success is claimed here.
- The D1-export Workflow, checksum manifest and clean-room logical restore drill are repository evidence only. No production backup, alert, point-in-time/logical restore or measured RPO/RTO has been completed.
- There is no deployed penetration test, dependency-policy gate, secret-rotation exercise or production access review in this workspace.
- Invocation logs and sampled Workers traces are configured in-repository, but deployed log retention, alerts, dashboards, trace continuity and incident-response evidence remain unverified.
- Automated Playwright/axe coverage does not replace manual screen-reader, keyboard-only, contrast and zoom acceptance.
