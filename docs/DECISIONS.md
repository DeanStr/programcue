# Product and engineering decisions

This file records durable decisions. It does not imply that every decided capability is implemented; verified delivery status lives in `IMPLEMENTATION_STATUS.md`.

| Decision                       | Outcome                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Product name                   | Program Cue                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Product shape                  | One pre-release TypeScript modular monolith; no backward-compatibility layer without a real external consumer or deployed migration history                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Frontend/runtime               | React Router framework mode with SSR, loaders/actions, resource routes and path navigation on one Cloudflare Worker                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Vertical-slice pattern         | Route → server authorisation/validation → application service → D1/R2/Queue/provider                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Large-module boundaries        | Keep stable service/repository/Queue facades at route and Worker boundaries; split implementations by current domain workflow, keep loader/action orchestration in route modules, and keep page-local state in one route-level container while extracting focused visual panels                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Visual direction               | Retain the Program Cue design language, but prefer a clearer and more appealing UX over exact prototype or Sessionboard parity                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Tenant model                   | One organisation with multiple events; private operational records and provider work are event-scoped                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Current event context          | Private browser routes resolve an explicitly selected, server-authorised event from an HttpOnly SameSite cookie. Production uses a Secure `__Host-` cookie; local/demo HTTP uses a separate non-`__Host-` cookie. A configured default may establish only the initial context, an unambiguous sole event may be selected automatically, and multiple events otherwise require an explicit audited switch. Unsafe requests without an established selection and invalid or unauthorised selections fail rather than falling back. Organisation-level owner and administrator memberships apply across that organisation; all other memberships remain event-scoped.                                                                                                                                                                                                                                                                                                                                                                     |
| Roles                          | Owner, administrator, committee chair, evaluator, submitter and speaker; the server, not hidden UI, is the permission boundary. Owners may grant/revoke administrator membership at current-event or organisation scope. Event administrators may invite only current-event administrators; organisation-wide grants and every administrator revocation remain owner-only.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Invitation acceptance          | A pending event or organisation invitation never grants access during navigation or prefetch. It requires an explicit same-origin event-selector POST, which atomically records acceptance and audit evidence. Every pending invitation has a finite expiry; missing, elapsed or revoked invitation state fails closed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Admin navigation               | Command Centre, Event Setup, Submissions, Review, Speakers, Resources, Schedule, Communications, Tasks, Programme, Integrations, Settings and Operations                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Command record search          | The permission-aware palette searches speakers, submissions, sessions, tasks, rooms, tracks, resource pages and the unified background-operation record. Domain aliases are parsed server-side and narrow the authorised record query; rooms and tracks open exact focused Event Setup records, while provider-specific communication and integration job kinds remain unified as operations.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Resource embed trust           | Resource embeds are limited to deployment-configured exact HTTPS origins, enforced both when immutable resource HTML is rendered and by response `frame-src`. Missing or malformed configuration fails readiness and resource saves reject unsupported origins instead of silently converting them to links. The default iframe sandbox grants no forms, scripts, popups or navigation exceptions; any future provider capability requires a named, evidence-backed policy rather than a generic per-embed permission toggle.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Admin visual shell             | Dark navigation with a light work canvas                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Participant/public density     | Comfortable light surfaces with mobile-responsive workflows                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Speaker workspace navigation   | Dashboard, Sessions, Tasks, Files, Resources and Profile are stable URL workspaces under one authenticated speaker shell. The dashboard summarizes readiness and links to the next action; each mutation is owned by the route for the affected resource rather than one hash-linked omnibus page.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Operational data grids         | Server loaders remain authoritative for cross-page filtering, ordering and pagination. TanStack Table owns only the loaded page's stable-ID selection, column visibility and density state; actions use the selected loaded records rather than inventing a client-side domain store. The submissions queue is capped at 50 records per server page, so TanStack Virtual is deliberately absent until measurement demonstrates a real unpaginated rendering need.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Form runtime                   | Form-js owns visual authoring and browser rendering, but a strict adapter maps only the supported component vocabulary into React Hook Form/Zod values before the normal server schema is evaluated. Form-js stays in a browser-only chunk, its watermark remains visible, and unsupported components fail rather than being silently discarded or rendered as a different field.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Canonical demo event           | Future of Events 2025, 20–22 May 2025, Toronto; demo powers require the explicit demo Worker configuration                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Repository authority           | D1 is always the transactional control plane. Each event explicitly selects D1 or Airtable domain-data authority. Airtable authority uses a managed typed schema, durable command/result intents and D1 projections for control/operations; missing credentials, schema divergence and failed recovery stop the operation, and D1 domain rows are never used as a silent data fallback.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Baseline migrations            | Until a migration is deployed/shared as immutable, update the pre-release baseline directly; afterward add numbered migrations                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Reference production slice     | Event Setup established server authorisation, event scope, Zod validation, optimistic revisions and append-only audit evidence used by later slices                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Time semantics                 | Store instants as UTC epoch values, but interpret event boundaries, date-only form/task deadlines and schedule slots in the event timezone; attendee-facing schedule times render in that timezone                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Person model                   | Canonical person identity with submission, session, membership and speaker associations                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Publication snapshots          | Public behavior comes from immutable form, resource, schedule-session/content/notes and communication versions, including identity/settings/audience/attachment metadata; mutable drafts do not alter the live version before a claimed publication boundary                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Form publishing                | Published form versions are immutable; later edits create a new draft, live public settings change only when it publishes, and existing applications retain their original schema snapshot                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Public draft intent            | A public application create/start intent derives one opaque, form- and actor-bound draft identity. Exact D1 retries recover only that matching draft; anonymous retries issue a fresh hashed bearer token and never persist or replay cookie plaintext. Reusing an intent across another form, version, event or owner fails rather than creating or claiming a different draft.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Resource publishing            | Resource title/slug/category, audience, acknowledgement policy and attachments belong to a version; acknowledgement records identify the exact version read                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Evaluation                     | Weighted criteria and explicit conflict declaration; owners/administrators hold decision authority, committee chairs require an explicit plan grant, and accepted released decisions create a session atomically and are final                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Schedule conflicts             | Event-boundary, room and speaker conflicts block publication by default; track and capacity handling follow the stored policy and are revalidated at publication                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Schedule interaction           | FullCalendar supplies list, time-grid day and time-grid week presentation plus pointer move/resize. Keyboard and form alternatives remain first-class, and every place, move, resize, unassign and short-lived undo is submitted to the same server schedule service for authorisation, version checks and conflict revalidation.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Public identity                | Event slugs are globally unique; canonical programme, embed, API, feed and calendar-session links are event-slug-addressed                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Published programme            | Public UI/API/feed read only the latest published schedule version; anonymous itineraries are durable under a hashed browser token                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Schedule content versions      | Session title, slug, description, track, format, duration, resources and visibility are snapshotted per schedule version. Administrator edits update the mutable session plus the active draft snapshot with compare-and-set/idempotent recovery, but never rewrite published or archived snapshots; public programme, Airtable projection and calendar consumers read the exact published version. Schedule notes belong to one schedule version and follow the same draft-only publication boundary.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| File lifecycle                 | Private R2 objects use opaque keys and remain quarantined until a trusted clean result releases a version; headless Uppy core/AWS S3 uses signed direct R2 multipart transfer for every valid file size, D1 plus R2 ListParts are authoritative for resume, and no browser hint, missing scanner or proxy-storage fallback may be treated as success                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Event file policy              | Every event stores one required, strict file-policy document. Administrators may lower the canonical headshot, slide, supporting-document and video limits in whole MiB; canonical maxima remain hard security bounds. Resource attachments, task evidence and other document uploads use the supporting-document limit. Initiation, resume, completion and the final metadata commit resolve the current event policy; no missing-policy or global-limit fallback is allowed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Accelevents reconciliation     | A terminal Accelevents run's downloadable CSV is rendered only from its tenant-scoped stored run, operation and per-run item/diff snapshot. It includes the prior/resulting external IDs, exact mapped payload/diff, statuses and errors, applies spreadsheet-injection protection, and never reconstructs historical results from current programme records or later provider mappings.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Accelevents export safety      | A live export requires the exact fingerprint returned by its approved preview/dry run. The durable request binds that fingerprint, mode and connection, and Queue work also snapshots the connection revision; preview drift, idempotency-key reuse with changed input or a provider/account reconfiguration fails before another external write.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Task completion undo           | A direct participant/admin completion may be undone for five minutes only with a server-issued single-use token and an atomic revision/evidence/dependency comparison; submitted, approved, waived, externally effective or subsequently changed work is not presented as reversible. The ordinary inline form/status remains the durable and no-JavaScript interface; Sonner adds a supplemental progress/status notification whose action and lifetime are bounded by the same authoritative token expiry, never toast-only validation.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Acceptance task plans          | Each task template explicitly declares whether acceptance auto-assigns it; there is no storage default. Accepted decisions atomically materialise active roots plus prerequisites in the same D1 transaction as the session and speaker relationships. Speaker, session and event scopes map to their real target IDs, dependency edges stay within one scope, existing template/target instances are reused without overwrite, and session-start anchors fail validation because a newly accepted session is intentionally unscheduled.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Communication safety           | A browser-composed communication starts as a revisioned D1 `communications` draft and the same row transitions atomically to scheduled or queued after authoritative preview and fingerprint-bound confirmation. Editing increments the revision and invalidates prior confirmation; reload loses only the ephemeral preview, not intent. Versioned content, event merge values, exact recipient/source snapshots and the verified sender identity then follow durable D1 intent → exact send claim → provider reconciliation. Active work freezes its sender fields; cancellation competes with the send claim, Resend receipts reduce monotonically by severity, and missing sender, Queue or credentials block delivery.                                                                                                                                                                                                                                                                                                            |
| Outbound webhook intent        | A domain mutation that advertises an outbound webhook atomically materialises the endpoint-scoped delivery, operation, item and audit/change evidence in the same D1 batch, guarded by the domain audit event. Queue dispatch happens only after commit; `operation_jobs.dispatched_at` distinguishes committed-but-undispatched work, and the minute scheduler recovers that narrow crash window. Missing Queue configuration fails before mutation when a matching endpoint exists, while a real post-commit dispatch rejection is recorded as `queue_failed` for explicit operational recovery rather than hidden or simulated.                                                                                                                                                                                                                                                                                                                                                                                                     |
| Email provider selection       | `EMAIL_PROVIDER` is explicit. Production accepts only Resend and requires its API key; the local demo, development and test runtimes may select Mailpit's HTTP Send API with complete endpoint/auth configuration. Auth, participant verification, transactional communication and email-ICS share the same send contract, preserve idempotency/attachments and record the provider's real message identifier. There is no provider fallback or SMTP compatibility path.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Calendar baseline              | Stable iCalendar UIDs and sequence-aware REQUEST/CANCEL operations; one current attempt serializes rapid lifecycle changes and stale completions are superseded. An active invitation stays bound to its provider and account until cancellation completes; it is never silently reused after a provider/account switch. Email-ICS, Google and Microsoft provider boundaries are explicit. Google/Microsoft connections use an authorised OAuth start/callback, encrypted refresh tokens and compare-and-set refresh/failure updates; missing applications or provider failures are reported, never simulated.                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Dashboard freshness            | D1 `event_changes` is authoritative; an event-scoped Durable Object broadcasts post-commit WebSocket invalidations and clients retain a bounded polling fallback of at most 30 seconds                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| API authentication             | Event-scoped, scope-limited API keys are stored only as hashes, revealed once, expirable and revocable                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| API contract                   | Versioned REST resources use strict Zod 4 validation, bounded bodies, RFC 3339 timestamps, cursor pagination and structured errors/correlation IDs. Registered command schemas deterministically emit the synchronized OpenAPI component schemas, while route operations remain explicit. API-key and participant commands persist atomic exact-replay results plus resumable notification, webhook and realtime effects. Human-identity review/communication commands retain their same-origin session boundary rather than synthesising a person for an API key. The API exposes only lifecycle commands whose service owns an actor/idempotency contract.                                                                                                                                                                                                                                                                                                                                                                           |
| AI/agent actions               | The event-scoped Cloudflare Agent reads only server-authorised evidence. Advisory actions cannot mutate. Consequential actions are allow-listed, persisted as exact proposals, previewed, explicitly approved and executed once through the normal domain service/communication boundaries with a renewable recovery lease and audit evidence; no unreviewed publish/send is available. Organisation owners select Workers AI, OpenAI Responses or Anthropic Messages with audited compare-and-set settings, and a missing selected binding/credential fails without provider fallback.                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Agents SDK dependency          | Pin the Cloudflare Agents SDK and its required AI/MCP peers to verified versions. Its decorators plugin uses Babel 8, so Program Cue declares Babel 8 at the application peer boundary while React Router retains its nested Babel 7 toolchain; `npm ls`, the Agent Durable Object test and both builds must prove that split remains valid. The supported local Node range starts at 22.18 (or 24.11+) to satisfy this production dependency graph.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Failure behaviour              | Missing auth, bindings, provider configuration and blocking invariants fail explicitly; no hidden storage, credential, stale-data or provider fallback                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Runtime modes                  | Only the checked production, demo, development and test mode pairs are accepted; contradictory or unknown `APP_ENV`/`DEMO_MODE` values fail before routing or Queue consumption, and unknown environments retain production-grade redaction and transport security                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Production readiness           | Production HTTP, Queue and scheduled entry points require the complete checked deployment binding/secret inventory and reject empty, placeholder or weak required values before work starts. `/api/v1/health` additionally exercises the D1 baseline. Readiness deliberately verifies local configuration and platform bindings, not live third-party availability; live provider checks remain deployment acceptance and cannot be silently replaced with simulated success. Production event IDs and public slugs are configurable, bounded identifiers rather than demo-identity invariants.                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Release identity and telemetry | HTTP, Queue, scheduled and backup-Workflow entry points fail readiness when `SOURCE_REVISION` is missing or invalid; production requires a hexadecimal Git revision and exposes it through health only as a non-secret release identifier. Request correlation prefers a validated Cloudflare Ray ID, then a machine-shaped caller UUID, then a generated UUID. Worker request, Queue, scheduler, backup and communication-dispatch logs record only bounded operational identity, safe provider/workflow labels and error classes; raw URL paths, payloads, prompts, secrets, personal data and exception messages stay out of those logs. Cloudflare invocation logs and traces are explicitly configured, while deployed retention, alerting and Forge evidence remain external acceptance.                                                                                                                                                                                                                                         |
| Evaluator reset                | The fixed demo event uses an explicit confirmed event-scoped cleanup instead of deleting the event row: non-terminal external work blocks reset, only that event's private R2 prefix is cleared, append-only audit history is preserved, and deterministic judged fixtures are reseeded; the route is absent in production mode                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Performance evidence           | Runtime budgets use an explicit opt-in Chromium lab harness. Its ordinary profile is multi-sample; its isolated deterministic fixture exercises the real server-paged submissions/speakers routes with 10,000 records plus real mutation, schedule, realtime and recovery paths. The fixture never enters demo data or the correctness gate. Hardware-sensitive timing assertions stay opt-in, and deployed p75/RUM and production-like scale acceptance remain separately required.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| D1 backup and recovery         | D1 Time Travel is the point-in-time mechanism; a daily Cloudflare Workflow uses the REST polling export API and a deterministic UTC-date instance ID, streams SQL to a separate private R2 bucket, and records an immutable SHA-256 manifest. Missing bindings, identifiers or token fail explicitly. Local restore drills prove repository mechanics, while a live backup/restore, alerts and measured RPO/RTO remain deployment acceptance.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Test coverage economy          | Prefer one authoritative test at the lowest layer that can prove an observable rule, then add browser coverage only for cross-layer behavior, accessibility or visual risk. Do not duplicate provider request contracts across generic and provider-specific suites, assert exact server-rendered markup already exercised in the browser, or run the primary Chromium smoke in addition to the complete Chromium behavior suite. A focused visual state may replace the same route's generic default snapshot when it still exercises the route at desktop and mobile widths; a component-catalog baseline is not retained solely as indirect coverage when real product surfaces exercise the same system. Firefox and WebKit retain explicit cross-engine smoke coverage. Route reachability tests must exercise route matching rather than search serialized configuration text.                                                                                                                                                                                                                                                  |
| Browser mutation origin        | Cookie-authenticated non-API mutations require an exact same-origin `Origin` header at the Worker boundary; API keys, signed webhooks and Better Auth keep their dedicated request protections                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Participant retention          | After an event's configured retention boundary, an organisation owner uses one preview/typed-confirmation workflow: legal holds, published forms, unerased files, active provider work and unreconciled calendar invitations fail closed; event-scoped participant links are replaced with stable random non-identifying pseudonyms and embedded PII/provider identifiers are redacted in bounded idempotent batches. Global identities shared with another event remain intact, while exclusive credentials are revoked. Completion atomically records `events.participant_retention_completed_at` and immutable audit evidence; subsequent calls revalidate the redacted state, and narrow database ingress guards reject participant PII without freezing audit, operation, generic webhook, programme-fact or recovery bookkeeping. Append-only audit rows, historical programme facts, unscoped security stores and external-provider records are explicitly retained/reported rather than silently rewritten or claimed deleted. |
| Excluded product scope         | General CRM, general marketing automation, payments, multilingual expansion and a general-purpose CMS                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
